假设一家店同意给顾客退 30 元。Agent 发出退款请求，支付侧处理成功，响应却在回来的路上丢了。进程重启时，本地订单还显示「退款中」。如果直接再发一次，而这笔订单还允许部分退款，第二笔 30 元也有可能退成功。

从 Agent 的位置看，它少了一条工具结果。换一个模型，它或许能想到先查订单，但它仍然需要知道该查哪一笔、之前用了什么参数，以及哪里有权确认结果。我读 Vercel 的 Workflow SDK 和 AgentRun 的资料时，想把这个例子走完。流程接得上之后，还要看顾客能不能看到正确的状态。至于这次摸索出来的做法，下次用之前也值得试一试。[前篇关于 Agent Loop 的文章](https://blog-sandy-psi-42.vercel.app/blog/20261007-agent-loop-first-look/post)

## 一、重启之后，靠什么认出同一笔退款？

我会在第一次调用支付接口之前，先保存一条退款意图。它有自己的操作 ID，并关联订单、原支付记录和已经核准的金额。若支付方支持幂等请求，这条记录还要保存此次使用的幂等键。模型重新规划、任务换机器跑，这条意图的身份都得保持一致。订单号本身不够用，同一笔订单可能有两次各自获批的部分退款。

执行器从已保存的退款意图里取参数，向支付方发请求。拿到响应后，把支付方返回的退款 ID 和状态也放回这条记录。这样，后来接手的进程可以沿着同一条记录查询。同一笔退款若需要重试，可以继续使用原来的参数和幂等键。

这个 ID 也要用在第一次派发之前。用户重按提交，服务端应根据同一个已获批的退款申请找到原记录。要是每按一次都新建一个操作 ID，支付方看到的就是两笔不同的退款，幂等键自然拦不住。另一笔确实经过审批的部分退款，才会对应新的操作 ID。

| 恢复时手里的证据 | 可以继续做什么 |
| --- | --- |
| 本地还未提交退款意图，且执行器只发送已经提交的意图 | 重做本地准备，再从已保存的记录发起请求 |
| 意图已保存，缺少支付侧结果 | 按支付方支持的方式核对，或在幂等约定允许的范围内用原键和原参数重发 |
| 支付方已受理，状态仍在处理中 | 保留退款 ID，等待状态更新或重新查询 |
| 已确认支付方退款成功，本地订单还没更新 | 用确认过的结果补上本地状态，无需新建退款 |

即使本地在发请求前已经写下「准备发送」，也可能在支付侧执行成功后、保存结果前崩溃。把数据库事务开得再久，它也管不到支付方的那次提交。两个 worker 若同时尝试恢复，我会让它们争抢同一条退款意图。更新本地状态时检查记录的版本，避免来晚的旧结果把已确认的状态改回去。本地锁失效或任务重新分配时，旧 worker 发出的请求可能已经在路上，所以两边发请求也得沿用这条意图绑定的幂等键。支付方缺少可用的去重能力时，接手的 worker 先核对结果，查不清就挂起这笔退款。

支付方的幂等承诺也有期限和范围。以 Stripe API v1 为例，服务端会保存已经开始执行的请求结果，同一个键可能拿到之前保存的 `500`。用同一个键改金额会触发参数检查，键被清理以后再用，也可能被当成新请求。再加上退款可以处于处理中，收到响应和退款完成之间还隔着一步。如果查询没有找到对应记录，我会先确认查询是否覆盖这次操作。到了去重期限之外，结果又没有查清，这笔任务就应该停在待确认。[Stripe 幂等请求](https://docs.stripe.com/api/idempotent_requests) · [Stripe 退款状态](https://docs.stripe.com/refunds)

Vercel Labs 的实验项目 `durable-harness` 把会话消息、正在处理的轮次和工具调用放进事件日志，让支持的 Harness 可以从记录恢复。已经有结果的步骤可以从日志取回，剩下的工作接着走。支付方有没有执行一笔尚未记下结果的退款，仍要靠支付接口提供的查询或幂等能力。[durable-harness 项目说明](https://github.com/vercel-labs/durable-harness)

回放也有成本。Vercel 在托管环境里用同一个 1,020 步工作流比较 `v4.8.12` 和 `v5.2.0`，中位完成时间从 21.0 分钟降到 3.0 分钟。增量回放是其中一项改进。在基准后段的采样区间，步骤间开销的 p75 从 1,748 毫秒降到了 70 毫秒。实际 Agent 的耗时还取决于模型和工具。[Workflow SDK 5 发布文与基准](https://vercel.com/blog/workflow-sdk-5)

事件日志和模型读到的上下文可以有不同的长度。恢复进程需要查到原来的操作 ID 和支付响应，模型这一轮可能只需要知道「退款已受理，正在处理」。我会让工具返回这条简短的状态，并带上可回查的退款 ID。这样既能在恢复时找到依据，也不用每次都把所有历史响应塞回模型。

## 二、日志显示完成，顾客看到什么？

假设恢复顺利，支付侧只退了那一笔。此时顾客打开订单页，还有可能看到「退款失败」。例如，后台在核对完成后补写了状态，页面却仍从缓存拿旧值。单测可以证明状态机允许这次更新，支付侧的记录也能证明钱已经退过。用户看到的结果，需要沿着实际页面再查一次。

我想把这段流程写成三个能重跑的用例。测试在受控环境里模拟故障，支付侧记录由测试夹具保存，便于验收者独立检查。

| 制造的故障 | 我会去哪里看结果 |
| --- | --- |
| 支付侧记下退款，返回响应前断开连接 | 恢复后查同一笔操作在支付侧的记录，金额仍是 30 元，再确认订单最终同步了已退款状态 |
| 支付侧暂时只返回处理中，用户再次提交同一笔已获批的退款 | 查两次提交是否落到同一条退款意图，刷新页面后仍显示处理中 |
| 本地更新订单后，进程在报告完成前退出 | 恢复后检查顾客页面和支付侧记录，确认只补齐任务结果，没有发起另一笔退款 |

只让支付接口的 mock 抛出超时，测试可能一直通过，因为支付侧根本没有发生过退款。要覆盖「对方成功、本地未知」，支付端的测试替身得先写入一条退款，再切断连接。两种情况下，调用方看到的都可能是超时。只有后一个用例能检查恢复以后有没有多退一笔。

Momentic 的 Jeff An 写过一个类似的验证盲点。富文本编辑器的加粗和下划线都能点，也各自有测试。但如果需求理解漏掉了「撤销应还原文本格式」，负责实现的 Agent 很可能也会漏掉那个测试。把验收交给另一个 Agent 时，我会给它原始需求、运行环境和观测入口。验收条件在执行前固定，测试报告也要能指向具体的操作步骤和可观察结果。把同一份写代码的聊天记录交给另一个模型，仍有可能把原来的假设一起传过去。[Jeff An 关于 Coding Agent 验证的文章](https://stackoverflow.blog/2026/11/13/your-coding-agent-shouldn-t-grade-its-own-homework/)

Momentic 还在四个开源应用上发布了 QA-Bench。在给定的 60 分钟配置里，Mo 平均找到了 19.3% 的已标注缺陷，Codex 和 Claude Code 最好的配置分别是 6.2% 和 4.2%。我会把数字读成指定浏览器配置、时间预算和标注集下的缺陷召回。几套工具的访问条件和实现都有差异，结果很难拆出多少提升单独来自验收上下文的隔离。真想研究这个问题，可以拿同一批补丁，固定模型、工具和预算，只改变验证者是否看到实现过程，再对照漏掉的验收项和误报。[QA-Bench 的任务与评分](https://huggingface.co/datasets/momentic/qa-bench#the-task)

简单条件依然适合交给程序断言。测试替身可以直接数这一笔操作产生了几次有效退款，浏览器检查则用来确认用户看到什么。开放性问题再留给验证 Agent，比如错误提示是否给了用户明确的下一步。这样复测时，既能定位是业务状态错了，还是界面解释不清，也知道哪些结论需要人看一眼。

## 三、这次学到的处理办法，什么时候能交给下一次？

一笔退款查清后，很容易留下这样一条经验：「接口超时就先查状态。」我会先追问两个细节。查询用的是哪一个 ID？查不到的时候，这个支付方允许我们得出什么结论？如果本次刚好遇到一个能按业务操作 ID 查询的支付方，换成只支持按退款 ID 查询的接口，原来的步骤就可能缺了必要输入。把一次成功压成一句话，也可能把成功依赖的条件压没了。

AgentRun 的做法是，在启用学习后，每次运行开始时固定一份经验快照。任务结束时，模型可以提出候选经验。事实、偏好或纠正可以记成 Notes，操作规程可以写进 Skills，足够稳定的步骤可以形成 Workflow 草案。候选经验会经过结构检查和模型评估，敏感的变更由负责人审核。已采纳的经验可以追查到来源，也可以停用或恢复。任务暂停后接着执行，仍然用最初拿到的经验快照。[AgentRun 的学习机制与版本说明](https://agentrun.ai/docs/self-improvement)

这个快照让我想到实际排查时的一个问题。假如一笔退款按旧流程走到「待确认」，此时另一条任务发布了新经验，允许在某个支付接口上自动重试。前一条任务如果恢复后马上吃到这次更新，就很难解释它为什么忽然改变了动作。固定经验版本可以让运行过程可追溯。真正发起写操作时，还是要重新确认当前的权限和支付状态，避免把旧流程里的判断当成新的授权。

拿这笔退款来说，我会给候选经验写清适用的支付方和接口版本，需要用哪个 ID 查询，幂等键过期后又该在哪里停住。还要记下它来源于哪次运行，后来在哪些样本上试过。

格式正确的 Workflow 草案可以进入试跑。查到成功的那组订单，应当用已有结果更新状态。仍在处理的订单继续等待，测试可以直接核对这一步有没有多发退款请求。查询暂时没有结果的订单，则要看流程是否会误判成可重试。采纳前也得跑一遍没有故障的路径，免得修好一个小概率故障，却让每笔普通退款都多查一次。

评测也可以沿用前一节的用例。先冻结一组没有参与经验抽取的订单，再各跑一组带经验和不带经验的任务。我要看的首先是两边的退款笔数和金额是否正确，未知状态有没有被提前写成成功。质量过线以后，再比较需要几次模型调用，用户等了多久，多少任务转给了人。算账时，还要把提取和评估候选经验的开销摊回同一组任务。调用次数变少，可能只是模型更早结束了。若证据也跟着变少，我宁愿再看一遍失败记录。[AgentRun 对重复任务评估的说明](https://agentrun.ai/docs/self-improvement#measure-improvement-over-repeated-work)

回到开头。服务重启后，我希望在这笔订单里能找到原来的退款意图，并看见支付方最后确认的状态。没查清的时候，订单页就写「退款处理中」或「待确认」，具体用哪一个，取决于支付方是否已经受理。等结果对上以后，再看看这段处理过程里，有哪一步确实值得下一笔订单少走一遍。
