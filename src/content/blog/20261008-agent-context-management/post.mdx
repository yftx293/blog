我想把这个博客一点点做成自己喜欢的样子。

有些地方已经想清楚了，有些还没有。可能今天觉得文章列表需要一个标签筛选，明天又觉得，先把第二篇文章写好更重要。一个个人项目，大概就是这样慢慢长出来的：做一点，看看效果，再决定下一点。

如果有 Agent 帮忙，我希望这些事情可以分几次做。

今天聊清楚范围，让它查查代码；做到一半，先停下来。下次回来，我可以说一句：“我们接着做那个标签筛选吧。”

我希望它能接上进度，也能记得哪些地方暂时别动。最好连我也不用重新翻完聊天记录，才能想起当时为什么这样决定。

这个期待很日常。落到工程里，却需要回答不少问题：上次的要求存在哪里？讨论过的方案，哪些已经否决？代码后来有没有变化？它现在说“继续”，继续的是哪一个版本的任务？

[上一篇](/blog/20261007-agent-loop-first-look/post)，我拆开了 Agent Loop：模型选择行动，工具执行，反馈把结果带回来。这次想顺着循环再往里看一步——**模型决定下一步的时候，究竟看见了什么？**

下面仍然用一个设想中的博客任务展开。它是一份帮助我理解机制的例子，还不是经过实际运行验证的案例。我想先把问题想清楚，以后遇到类似偏差时，知道该留下什么记录、从哪里查起。

## 一、明明刚说过，为什么还是改了？

假设我把这样一个任务交给 Coding Agent：

> 给文章列表加一个标签筛选，保留现有 URL 结构。

它读了页面代码，检查标签数据，提出几种实现方式。中间，我又补了一句：

> 先做页面内筛选，不新增路由。

过了一会儿，筛选做好了，但 URL 结构也变了。

我的第一反应大概会是：“刚才不是说过了吗？”

这种感觉很容易理解。要求就在聊天窗口里，往上翻一点就能看到。可我们眼前完整的聊天记录，与模型执行那一步时真正收到的输入，需要分别确认。

原始约束可能没有进入后续调用，也可能在历史压缩时被漏掉。还有一种情况：它一直在输入里，模型仍然选了不合适的方案。

甚至，问题从一开始就存在。“保留 URL 结构”，我指的是路径和参数都不动；它理解成文章地址不变，允许增加筛选参数。两边都觉得要求很明确，直到结果交回来，才发现说的不是同一件事。

这些原因对应着不同的修法。遗漏的信息需要接上，含糊的要求需要澄清，已经明确却没被遵守的约束，则要继续检查判断、执行和验收。

所以，我会先把三个问题分开：

- 那条约束有没有进入执行前的输入？
- 它的含义和适用范围是否清楚？
- 最后的行动有没有满足它？

信息存在，不代表行动一定遵守；行动出错，也不能反过来证明信息已经丢失。

有些产品不展示完整的模型输入。那就只能根据对话、交接摘要和工具记录缩小范围，暂时保留几种解释。单看最后的回答，无法准确还原偏差发生在哪里。

我觉得这种克制很有必要。我们希望 Agent 如实报告自己知道什么、没确认什么，解释它的错误时，也应该遵守同样的标准。

## 二、聊天窗口里的连续，与调用里的连续

聊天界面给人的感觉，是同一个 Agent 一直坐在对面。

它刚读过文件，接着讨论方案，然后继续修改。对话没有中断，我们也很自然地认为理解会一直延续。

但对于常见的 LLM Agent，运行系统需要为每一次模型调用准备输入。这里的“一轮”，指一次模型调用；用户的一次请求，可能经过很多轮调用才完成。

在标签筛选任务里，这份输入可能包括：我的要求、项目约定、工具说明、此前的消息，以及刚刚读到的代码和检查结果。具体保留哪些、怎样排列、有没有截断，取决于系统实现。

Anthropic 在[上下文工程的文章](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)里，把关注点从提示词扩展到工具、外部数据和消息历史，并强调这些信息需要在运行过程中持续整理。

对我来说，这让“上下文”变得具体了：**它是当前这一步判断能够依据的信息。**

仓库里有一份 `AGENTS.md`，需要被加载，才有机会影响这一轮；完整日志存在磁盘上，需要被读取，才会成为当前依据。文件保存着，与模型此刻能够使用它，是两个环节。

可以把这个过程粗略看成一条链：

```text
任务要求与外部材料
        ↓
读取、检索、筛选、整理
        ↓
当前调用的输入
        ↓
模型选择行动
        ↓
工具执行并返回结果
        ↓
更新下一轮所需的信息
```

这里多出来的工作，是“更新”。

一次新的观察，可能确认旧判断，也可能推翻它。用户补充了一条要求，任务范围就可能变化。工具执行失败，原先计划的下一步也许已经不成立。

如果只是把新消息追加进去，却没有把变化表达清楚，输入里就可能同时出现几个互相冲突的版本。

因此，我越来越觉得，上下文管理涉及的是任务理解怎样延续。模型接到的材料，要能够说明：现在以什么为准，哪些仍然有效，哪些已经改变。

## 三、信息留下来了，也可能已经过期

任务变长之后，有一种偏差比“忘记”更隐蔽：旧信息还在，而且看起来很可信。

Agent 第一次读组件时，页面确实没有筛选状态。后来它已经加上了状态管理，但第一次读取的结果仍然留在历史里。如果没有区分前后，它可能继续依据旧代码分析问题。

检查结果也有有效范围。

“测试通过”对应的是某个时刻的代码，以及某组检查。后面又改了一段逻辑，前面的通过记录就不能直接证明当前版本没有问题。类型检查通过，也不能独自证明筛选在浏览器里能正常使用。

我会更愿意看到这样的记录：

> 修改筛选状态之后，类型检查通过；随后调整了标签按钮，尚未重新检查，也未验证浏览器行为。

它没有“全部完成”那么干净，却给下一步留下了清楚的起点。

还有一种需要保留的区别，是信息本身的身份。

“可以考虑新增路由”是候选方案；“决定新增路由”是选择；“已经新增路由”是执行状态。如果摘要只写“讨论了路由方案”，接手的人就需要猜测发生到了哪一步。

排查问题时，猜测与事实也容易混在一起：

> 筛选没有结果，怀疑标签字段不一致，尚未核对。

如果被整理成：

> 标签字段不一致导致筛选失败。

一个待验证的假设，就变成了后续调查的前提。

这会影响 Loop 修正错误的能力。模型原本可以用新的反馈推翻假设，但如果反馈被整理成旧假设的证明，循环转得再久，也可能一直围着同一个误解打转。

所以，我想在重要记录里保留几个简单标记：这是用户要求、直接观察、暂时推测，还是已作出的决定？对应哪个版本？还有什么没确认？

此外，外部材料也有自己的身份。网页或文件里出现一句命令，不意味着它获得了修改任务要求的资格。整理上下文时，来源与用途应该一起留下，避免材料内容被误当成执行指令。

这些区别看起来很琐碎，却决定着下一轮是在继续调查，还是在重复一个越来越像事实的猜测。

## 四、压缩历史时，应该为谁保留什么？

保留全部历史，看起来最保险。

但一次任务可能产生大量搜索结果、重复报错和中间讨论。下一轮真正要做的事，未必需要重新读完这些材料。上下文有容量限制；即使还放得下，材料之间的关系也需要清楚。

压缩因此是一种合理选择。Anthropic 将 compaction 描述为概括接近窗口上限的对话，再以摘要延续任务，同时提醒过度压缩可能丢失关键细节。[关于上下文压缩的说明](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

难处在于：整理时，我们未必已经知道哪条细节会在后面起作用。

回到标签筛选，这份摘要就有些危险：

> 正在实现标签筛选，主要修改已完成，继续检查。

它保留了进度感，却丢掉了 URL 约束、否决过的方案，以及“完成”具体指什么。

如果我要准备交接，会更愿意写成这样：

```text
目标：
给文章列表增加标签筛选。

本次范围：
只做页面内筛选，保留现有 URL 结构，不新增路由。

当前状态：
已加入筛选状态和标签按钮。
尚未验证切换标签后的列表显示。

已否决：
通过新增路由实现筛选。
原因是超出本次改动范围，不代表以后永远不能采用。

待验证：
全部文章、单个标签、无匹配文章三种状态。
当前修改是否涉及路由。

证据入口：
相关组件位置、当前 diff、最近一次检查记录。
```

这份记录的价值，在于接手后不用重新猜测目标、边界和当前位置。至于完整代码与日志，可以通过留下的入口继续核对。

其中，我尤其想保留“为什么否决”。

一个放弃过的方案，下次看起来仍然可能很合理。只有结果，没有理由，Agent 就可能重新探索一遍；只有“禁止”，没有范围，一次临时取舍又可能被延续成永久规则。

我也会把“待验证”当作交接的重要部分。

整理材料时，我们很容易优先保留已经得到的结论。但未解决的问题决定着下一步该做什么。删掉了它们，摘要可能非常流畅，任务却失去了继续调查的方向。

当然，交接文本仍然可能写错。Agent 的自述、工具返回和当前环境，属于不同层次的证据。“文件已经保存”可以再看文件，“检查通过”可以核对运行记录。关键状态需要与现实重新对齐。

一份好的摘要，应该帮助下一轮找到证据，也允许证据纠正摘要。

## 五、记忆需要有效期，也需要出口

想到交接，很自然会想到长期记忆：把重要信息存下来，以后就能继续用。

但存什么、存多久，仍然需要判断。

项目代码风格是相对稳定的规则；标签筛选改到哪一步，是当前状态；一次失败的实现方式，是历史经验。它们适合不同的维护方式。

“目前没有实现筛选”，完成任务后就该更新。

“这次先不新增路由”，适用于这次任务。

“以前用某种方案遇到问题”，值得保存，但下次使用之前还要看原因是否仍然成立。

记忆越容易被反复读取，旧错误也越容易反复进入判断。积累记录的同时，需要给记录留下更新和失效的办法。

我会先问几件事：这条信息适用于什么范围？来自哪里？是否确认过？什么变化发生后，应该重新核对？

至于原始材料，不必每轮全部加载。可以先保留必要信息和检索入口，需要时再读取。工具返回也可以通过过滤、分页和范围选择控制体量，并说明怎样获取被省略的部分。[Anthropic 的工具设计建议](https://www.anthropic.com/engineering/writing-tools-for-agents)

不过，有些信息不能放心地交给“需要时再找”。

当前目标、不可越过的约束、尚未解决的关键问题，应该在继续执行前明确可用。Agent 如果根本不知道某条限制存在，就未必会主动搜索它。

我的倾向是：先保证继续工作所需的最小完整信息，再让细节能够按需取回。“最小”要服务于完整，不能为了短，把任务边界也一起删掉。

还有一条界限。规则文件可以表达工作约定，真实的读写权限仍需要执行环境落实；历史记录中的“以前允许过”，也不能替代当前操作的授权检查。

记忆可以帮助理解过去，当前行动仍然要面对当前条件。

## 六、任务跑偏之后，我会从哪里查起

如果以后真的遇到标签筛选改了 URL，我想留下一个可以重新检查的小案例。

我会优先找三个位置：最初的要求、执行关键修改之前可见的记录，以及修改后的实际结果。

沿着这三个位置，对照那条约束：

它在最初是否明确？中间有没有被改写？交接时有没有留下？最后的检查有没有覆盖它？

这样，即使无法看到完整输入，也能逐步排除一些解释。

例如，摘要里已经没有 URL 约束，信息传递就是值得调查的地方；摘要保留得很清楚，修改仍然违反要求，就要继续看执行判断与验收。若双方对“URL 不变”理解不同，则应先把具体标准写出来。

修复之后，也应该保留原始失败案例。换一种摘要格式是否有帮助，增加一次路由检查是否能发现问题，后续都可以用它验证。

我不会因为某次修改后成功，就急着认为找到了唯一原因。模型输出可能变化，运行环境也可能变化。案例能帮助判断，结论还需要与验证范围相称。

这也让我重新看待验收。

关键约束如果能变成具体检查，就多了一条独立的反馈通道。保留 URL 结构，可以检查路由差异和实际导航；筛选能用，可以验证几种列表状态。目标中仍有人的取舍，比如交互是否自然、复杂度是否值得，那部分就把结果带回来讨论。

上下文让 Agent 有依据继续，验收让它的理解有机会被结果检验。两者都需要，前者再详细，也不能省掉后者。

## 七、我想留下的，还有决定背后的理由

讨论到最后，我发现自己最在意的上下文，常常是那些容易被整理掉的理由。

为什么这次不新增路由？

可能是为了控制改动范围，也可能是不想影响已有链接。为什么先做简单版本？可能是想看看自己会不会真的使用这个功能，还没到需要完整架构的时候。

这些理由未必需要每轮都重复。但当 Agent 准备调整方向时，它们应该找得到。

同一句“先做简单版本”，背后如果是赶时间，后续可以补齐；如果是有意控制复杂度，继续增加功能就需要更谨慎。

理由让一个决定带着自己的适用条件，也为重新讨论留下入口。

我希望 Agent 能发现原方案的限制。如果页面内筛选无法满足目标，它可以说明发现了什么，哪些要求受到影响，有哪些选择需要我来决定。这样的介入会让我愿意参与，因为它已经替我完成了一部分调查。

但发现一个更好的方案，与获得改变范围的授权，仍然要分开。目标可以变，变化应该被明确记录。

我不想为了防止跑偏，提前把每一步都写死。更愿意把目标、边界和重要理由交代清楚，让它在其中选择路径。遇到新证据时，再一起更新判断。

对我来说，这也是上下文管理里有人情味的部分：我们愿意认真保留彼此为什么这样想，也允许这些想法后来发生变化。

## 最后，留一个下次能接上的地方

回到这个还在慢慢长出来的博客。

标签筛选也许今晚做不完。文章还没写完，我可能先去做别的事。下次打开项目时，我希望看到一份不长、但可靠的记录：哪些已经做了，哪些还没检查，为什么暂时采用这个方案，以及现在最值得继续的一步是什么。

如果有地方不确定，就照实留着。

“还没验证”不会让我失望。它至少告诉我，我们应该从哪里重新开始。反倒是一句过早的“全部完成”，可能让我在下次继续时，多花一段时间弄清真实情况。

我对长期协作的期待，正在变得具体。

Agent 可以不一次就做对，也可以在看到新证据后改变判断。重要的是，改过什么能查到，暂时相信什么说得清，缺少的信息能够重新取回。这样，前面花过的时间才更有机会成为后面的基础。

我自己也会忘记当时的理由，也会把一句还没想清楚的话说得过于简略。一份好的任务记录，同样能帮助我接上自己的思路。

以后这个博客会有更多文章、更多改动，也会积累更多被否决的小想法。我希望那些经历能留下恰当的痕迹，让继续工作的人不必每次都从头猜。

下次说“接着做吧”的时候，最好我们都知道，昨天停在哪里。

至于接下来往哪走，可以看过眼前的结果，再慢慢商量。
