做 Agent 开发这段时间，我有个挺反常的体感：
一段外围代码写得越成功，它在下一次模型更新后被我们高高兴兴删掉的概率，就越大。

拿“提醒 Coding Agent 跑测试”来说。
这原本是一件需要认真设计的事。你让模型改一段代码，它很乐意写完，然后拍拍手告诉你任务结束。但对开发者来说，写完只是一半。有没有破坏原来的功能？测试过没过？刚刚的修改真的解决用户问题了吗？

如果模型还没养成这些习惯，我们就得在外面提醒它：给它塞一张待办清单，或者把验证硬编码进执行流程里。

过了一段时间，新模型发了。
你发现不需要再反复叮嘱，它自己就会去看报错、跑测试，甚至在结束前重新检查一遍工作。那段曾经十分有用的提示词和外围逻辑，突然就显得啰嗦起来。

今年 9 月，Codex 的负责人 Tibo Sottiaux 在 [The Pragmatic Engineer 的访谈](https://newsletter.pragmaticengineer.com/p/building-codex-with-tibo-sottiaux)里聊过这个变化。他把 Harness 形容为“总比模型稍稍领先一步的东西”：当模型还不能稳定完成某件事，系统先在外面扶它一把；等模型真的学会了，原来的提醒就可以退场。

这也是为什么，Codex 的开发者消息随着模型进步，正在变得越来越短。

我第一次认真想这件事时，感兴趣的倒不是究竟删掉了多少行代码，而是另一件事：
**如果我们为 Agent 设计的东西注定会不断失效，那我们到底在建造什么？**

## 一段代码短暂的一生

先把 Harness 说得简单些。

模型本身会生成文字、选择动作，但要让它在真实环境里干活，总得有东西把它接到外部世界：准备这一轮的上下文，提供文件和命令行工具，执行调用，保存会话，在失败时恢复，必要时还得拦截一个危险动作。

围绕模型的这套运行与协作机制，我们通常叫它 Agent Harness。

它不是某个固定的框架名字。一个终端里的 Coding Agent、一套常驻的个人助手，或者处理真实业务的 Agent，都有自己的 Harness。要解决的问题不同，长得自然也不必一样。

在早期阶段，Harness 经常像一位耐心的老师。
模型不擅长拆任务，就替它写好步骤；模型容易在长任务中半途而废，就设置进度记录；模型看不懂工具返回的报错，就加上重试和提示。每一个设计可能都很小，却足以改变真实的使用体验。

有趣的是，这些设计的成功，也在暴露自己。

当一种做法在足够多的任务中被证明有效，它就不再只是某个工程师的技巧。模型研究者会去研究这种行为，训练和评测会让模型逐渐掌握它。曾经靠外部流程维持的习惯，开始成为模型本身更自然的选择。

Anthropic 在今年[关于 Managed Agents 的文章](https://www.anthropic.com/research/managed-agents)里给过一个很好的例子：某一代 Claude 会在接近上下文边界时提前结束任务（他们管这叫 context anxiety），团队因此在 Harness 中加入了上下文重置机制。后来换用能力更强的模型，这种行为问题消失了，原来的重置措施反而成了负担。

这让我觉得，很多 Harness 设计都有一种鲜明的时代性。
它们记录着某一代模型的不足，也记录着人们如何绕过这些不足，先把产品做出来。

如果把代码看成一份永久资产，删除当然让人可惜。但如果把它看成一座临时架起来的桥，事情就不同了。桥让人先过了河，后来有了更好的路，拆掉它不意味着当初修桥是错的。

## 往前走，缺口也跟着往前走

今年 10 月，Jediah Katz 在 AI Engineer 的演讲[《Is the Agent Harness Dead?》](https://ai.engineer/talks/7Y4sbZgBdnc-is-agent-harness-dead)里，用 Data Flywheel（数据飞轮）描述过这个现象。

Harness 先帮助模型完成更难的任务。任务变得可用，真实使用就会带来更多尝试、反馈，以及可能被用来改善模型的数据。随着模型能力提高，旧的辅助措施被撤掉。然后，人们又开始把 Agent 推向过去做不到的事情。

我觉得这里最值得注意的，不是 Harness 一直在缩小，而是**模型与 Harness 之间的边界始终在移动**。

最早，我们希望 Agent 能自己修改文件；后来希望它能在一个陌生仓库里查明问题；再后来，希望它跨越多次会话继续工作，独立验证结果，甚至在几天时间里与其他 Agent 分工。
每当其中一部分变成普通能力，新的困难就浮出来了。

因此，这个过程在我看来更接近一个循环：
模型暂时做不到的地方，由 Harness 先补上；有效的做法在使用中得到检验，其中一部分被后来的模型学会；旧的支撑被卸下，系统随之变得轻一些；而人们已经开始要求 Agent 做更多的事，于是又出现新的缺口。

这里还有一个很实际的区别。并不是每个 Agent 产品都会把自己的运行记录拿去训练模型，也不是每次 Harness 改动最终都能变成模型能力。对大多数开发者而言，能直接参与的循环更朴素：观察失败，改变工具或流程，用评测验证，再决定保留还是撤掉。模型训练可能发生在这条经验链的另一端，也可能完全没有发生。

即便如此，两端仍然在相互推动。一代模型把昨天的困难变成日常，开发者才有余力提出昨天还显得奢侈的要求。

这也解释了为什么“模型越强，Harness 越薄”和“Agent 系统正变得越来越复杂”这两句看似矛盾的话，能够同时成立。
前一句说的是某些行为补偿，后一句说的是 Agent 正在进入的工作世界。它们观察的，根本不是同一个位置。

## 那些不会被学进参数里的东西

不过，循环并不会把所有东西都卷走。

模型可以学会什么时候该运行测试，但测试结果仍然得由真实的程序给出；它可以学会谨慎对待危险命令，但文件权限仍然需要操作系统或沙箱来执行；它也许能规划一周的任务，却不能凭一句“我记得”，让昨天的进程、尚未完成的动作和外部系统的状态自动延续到今天。

这不是因为模型在这些事情上还不够聪明。
我们不应该把“知道应该怎么做”和“现实已经按要求发生”当成同一件事。前者属于判断，后者需要外部世界回应。模型可以越来越擅长前者，但后一部分依然涉及计算资源、状态、时间和人的授权。

2026 年，Anthropic 在[介绍 Managed Agents](https://www.anthropic.com/research/managed-agents)时，把这个问题讲得很透彻。他们不再把 Agent 的整个生命局限于一次上下文窗口，而是尝试提供能够长期使用的会话、执行环境和稳定接口。
模型会变，具体的工作技巧也会变，但有些承载工作的抽象，需要活得比任何一代模型都久。

还有一些东西，甚至不属于通用知识。
一个 Agent 可以在公开资料上学到如何写商业邮件，却不知道今天上午刚发生的一次客户沟通；可以理解软件项目通常怎样协作，却不知道某个团队为什么在三个月前否决过一种方案。

事实会过期，偏好会改变，承诺有对象，权限也有范围。这些东西存在于正在发生的生活和工作里，而不只是训练数据里。

Harrison Chase 在[《Your harness, your memory》](https://www.langchain.com/blog/your-harness-your-memory)中谈到记忆时，提出过一个值得留意的问题：当长期使用的记录和经验都依附于某个封闭的运行系统，你交出去的可能不只是一次模型调用，还有对自己积累下来的上下文的控制。

模型会越来越懂得如何使用记忆。但记忆由谁保存，何时更新，能够向谁开放，出了错误能否更正，这些事情仍然需要真实的制度与系统。

我想，Harness 最后留下来的，未必是一套庞大的“智能增强装置”。
它可能更像一组朴素的约定：哪些事实值得保存，哪些动作必须确认，执行中断后怎么接上，出错之后谁能看到证据，以及谁最终为结果负责。

## 留下来的代码，也未必最值钱

走到这里，不妨再问一个不太浪漫的问题：
一项能力没有被模型吸收，就一定值得自己长期维护吗？

未必。

文件读取、命令执行、工具协议、会话存储，这些能力可能长期需要留在模型之外，却也可能逐渐成为大家都可以使用的公共设施。曾经需要自己写几千行代码的东西，某一天只需安装一个库，或者接入一个服务。

从使用者的角度，这是进步。从开发者的角度，它提醒我们：**代码必须存在，与这份代码必须由我来写，是两回事。**

真正能够沉淀下来的东西，往往藏在更具体的地方。
例如，一组来自真实任务的失败样本，知道系统在哪些条件下会犯错；一套能复现这些问题的评测，让开发者在换模型之后有依据地删除旧规则；一种能保存长期工作记录、允许人纠正和接管的方式；以及对某个领域中“什么结果才算完成”的深刻理解。

这些东西不一定会让演示视频更惊艳，却决定了系统能不能随着模型迭代而持续变好。

我很喜欢用一个小问题来判断某项 Harness 设计值不值得继续投入：
**如果明天可以把模型换成更强的版本，这个系统会自然变好吗？**

如果答案是肯定的，说明外面的结构给新模型留出了发挥空间。如果换一次模型就必须重新调整一整套脆弱的提示词、分支和例外规则，那么今天看起来很聪明的设计，明天也许会成为一道门槛。

当然，好的 Harness 不一定是最少的代码。有时候，增加一道真实的权限检查、一个可靠的任务状态，或一份能追查错误的记录，反而是让系统更自由地使用强模型的前提。

我越来越在意的是：一项设计究竟在替模型作判断，还是在为它提供完成工作所需要的现实条件？
前者应该经得起被删除，后者则值得认真建设。

## 写在下一次模型更新之前

回头再看“Agent Harness 已死”这种说法，我能理解它为什么吸引人。

每当模型的能力跨过一道门槛，我们总能看到一些旧技巧突然失去光彩。以前精心安排的步骤，现在一句话就够；以前靠规则纠正的行为，现在模型自己就会。

可如果只盯着这些被删掉的东西，就会错过另一半故事。

Harness 曾经把模型带到它还不能独自抵达的地方。后来模型学会了走这段路，人们便把目光投向更远处。下一代 Harness 也许会有更少的提示词，却要承担更长的任务、更复杂的协作，以及更多来自现实世界的责任。

我不太愿意把这叫作某种胜负。模型和 Harness 从来不是两支争夺领土的队伍。它们只是以不同的速度改变着同一件事：我们究竟能够把多少工作，放心地交给一个 Agent。

对于开发者来说，这或许是一种很好的提醒。做一项新功能时，可以认真想清楚它是为当前模型搭的一段台阶，还是未来也需要的地基。

台阶不必永远留着。只要它曾经让我们走到新的地方，就已经有了意义。
至于地基，最好经得起下一代、再下一代模型的到来。

我想这也是为什么，比起 Harness 会不会消失，我现在更关心另一个问题：
**当模型学会了我们昨天教它的事，今天终于腾出来的双手，准备拿去做什么？**
