> 帮我从照片库里找三张雨后的街景。横向，画面空一点。先给我看，别动原图。

“三张”“横向”“保留原图”，都容易说清楚。“画面空一点”就没有那么确定。

可能是人少一些，也可能是颜色不要太杂。街边有一盏灯，未必让人觉得拥挤；空无一人的街道，也可能被招牌塞得满满当当。有时候，看到候选之后，我们才知道自己想留下什么。

如果把这个任务交给 Agent，它已经接上了搜索、预览和图片处理工具，事情能不能顺利完成？

工具有了，仍然可能选错：标签写着“雨后”，画面里却看不出雨的痕迹；原图构图不错，裁切之后却只剩一块墙；它说“这张很安静”，实际上连预览都没有读到。

遇到这些情况，我会先忍住更换模型的念头，沿着调用过程看一遍：它选择了什么工具，工具实际做了什么，又把哪些信息带了回来。

这里用一个设想中的照片任务展开，还没有实验结果。想讨论的是：**工具怎样把一次请求接到现实里，又怎样让接下来的判断有据可依。**

## 查询的范围，需要先说明白

假设搜索工具接受这样的请求：

```json
{
  "query": "雨后的街景",
  "orientation": "landscape",
  "limit": 3
}
```

字段齐全，类型正确，`orientation` 也在允许的取值范围内。请求看起来没有问题。

但 `query` 究竟搜索什么？

如果实现只匹配文件名，它搜索的是字符串；如果匹配人工标签，它依赖整理者留下的描述；如果使用图像向量检索，它才可能根据画面语义寻找相近内容。

同一份参数，在不同实现里，问的是不同的问题。

Function Calling 可以让模型以结构化形式提出工具请求。Schema 则能约束字段、类型和取值范围。但格式检查无法独自证明，这次调用符合任务的意思。一个完全合法的请求，也可能走向一条不适合的路径。

[MCP 的工具规范](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)用 `inputSchema` 描述输入结构，同时提供工具描述。对这个例子来说，两部分都要认真写，执行端也需要真正落实校验。

我会把搜索工具的范围写得具体一些：

> 搜索照片的文件名和人工标签，不识别画面内容。多个关键词按“全部匹配”处理。`limit` 表示最多返回多少条记录，不保证有足够结果。操作只读。

这些说明没有增加底层能力，却能减少几种本来可以避免的误解。

知道检索范围之后，模型可以先用“雨后”“街道”寻找候选，再读取预览。如果没有匹配，也能考虑标签是否不完整、关键词是否过窄，而不必立刻断言照片不存在。

“最多三条”也与“找到三张合适的照片”有距离。工具完成的是一次查询，候选是否合适，还要继续判断。

我越来越觉得，接口里最值得补清楚的，往往是实现者已经习惯、因而没有写下来的条件：默认怎样排序，关键词如何组合，空结果意味着什么。这些条件对开发者可能很熟悉，对模型却仍然是未知的。

## 结果里，要留下继续寻找的线索

搜索返回空数组时，Agent 能说“照片库里没有雨后的街景”吗？

如果只有部分照片打了标签，这个结论就太大了。空结果只能说明，在当前可搜索的范围内，没有找到匹配记录。那些尚未整理的照片，仍然没有被排除。

返回三张也一样。它们可能只是按时间排序后的前三条，后面还有更合适的候选。

我会让结果保留检索范围、匹配依据和分页状态，例如：

```json
{
  "search_scope": "filename_and_manual_tags",
  "total_matches": 18,
  "next_cursor": "cursor_02",
  "items": [
    {
      "photo_id": "p_017",
      "revision": "r4",
      "matched_on": ["tag:雨后", "tag:街道"],
      "width": 4032,
      "height": 3024,
      "preview_ref": "preview:p_017:r4"
    }
  ]
}
```

这些是这个设想中的业务字段，并非 MCP 要求的固定格式。

`matched_on` 解释这张照片为什么被找到。`next_cursor` 提醒模型后面还有结果。`search_scope` 则帮助它判断，这次查询能够支持多大范围的结论。

一份结果既需要让模型知道“找到了什么”，也需要交代“还有什么没有找完”。

当然，返回整座照片库也未必有帮助。大量无关记录会占用上下文，关键线索反而更难被注意到。先返回足以筛选的信息，再按需读取细节，是一种可以尝试的安排。Anthropic 的[工具设计文章](https://www.anthropic.com/engineering/writing-tools-for-agents)也讨论了过滤、分页和有意义的返回内容。

只是，压缩结果时要留意后续调用需要什么。

照片 ID 用来读取同一张照片，版本标识用来核对它是否发生变化。用户说“第二张”时，系统还需要把这句话对应到刚才那一组候选。重新查询之后，排序可能变了，不能继续靠位置猜。

版本字段也需要有实际机制支持。后续读取或导出时，如果没有核对版本，那么 `revision` 就只是一行看起来严谨的文字。

这些信息不一定都展示给人，但要在调用之间接得住。否则，搜索时选中的是一张，处理时拿到的却可能是另一张。

## 图片信息和图片，隔着一步

结果里有 `preview_ref`，还不意味着模型已经看到了照片。

它只是一个可以继续读取的引用。运行系统需要获取对应内容，再把图像提供给支持视觉输入的模型。如果最终进入上下文的只有一段路径文字，模型仍然没有获得画面。

这一步很容易被“读取成功”四个字盖过去。

工具可能成功返回了一条数据库记录，也可能成功下载了图片文件。它们各自完成了一项操作，但模型是否获得了可用的图像输入，还需要单独检查。

在这个任务里，我会把判断依据分开看：

| 已获得的信息       | 能够支持的判断                     | 仍然不能证明           |
| ------------------ | ---------------------------------- | ---------------------- |
| 文件名、标签、尺寸 | 是否值得作为候选，是否满足尺寸条件 | 画面是否空，主体在哪里 |
| 实际提供的图片预览 | 预览中可见的内容和构图             | 原图细节，最终裁切效果 |
| 实际提供的裁切预览 | 这个裁切版本保留了什么             | 用户是否喜欢它         |

这样区分以后，排查会具体很多。

如果模型只有标签，却开始解释光线和构图，应当先检查图像有没有进入输入。如果清晰的预览已经提供，它仍然认错了主体，才继续检查视觉能力和判断过程。

**工具返回什么、系统实际传入什么、模型据此声称知道什么，需要对应起来。**

这也是工具设计与上下文管理接上的地方。上一轮确实获取过图片，但下一轮若只保留了“已查看照片”的摘要，后续判断仍然可能缺少画面依据。流程上经过了一步，并不保证这一步的信息会一直可用。

## 把确定的处理交给代码

原任务只要求展示候选，所以 Agent 应该先停在这里。

如果后来选中一张，并明确要求生成横向版本，才进入裁切和导出。

这时，一个宽泛的 `process_photo` 可能让模型决定很多事：裁切区域、输出尺寸、压缩参数，以及是否覆盖原文件。灵活性很高，也意味着每次调用都要做更多选择。

对于当前任务，我会先设计一个范围更清楚的 `create_crop_preview`：接收照片 ID、版本和目标比例，生成预览副本，返回预览及实际使用的裁切区域，保留原图。

固定的图像处理可以由代码完成，模型再比较裁切后的画面。

但即使工具内部有默认构图算法，也要留下调整的入口。居中裁切可能切掉街边的一束光；保留主体，也未必保留了用户想要的留白。处理规则可以给出一个起点，不必替所有偏好做最终决定。

工具粒度的选择，实际上是在分配判断。

拆得太细，模型要维护很长的操作链；合得太大，重要取舍又可能藏进实现里。我会用两个问题检查这个边界：这部分有没有明确、稳定的处理规则？结果不合适时，能否找到原因并局部调整？

“不改原图”则应该直接落在执行层。让工具只生成新文件，或者限制它只能写入独立的输出目录，都比单独依赖一句提醒更踏实。

工具描述帮助模型选择行动，执行代码负责约束行动。两边都做好，模型才有空间处理那些真正需要判断的部分。

## 没收到结果时，先别急着重试

假设导出工具运行了几秒，然后超时。

Agent 此时确定的是：它没有收到完整结果。至于文件有没有生成，还不知道。

如果把“没收到成功消息”当作“操作没有发生”，接下来就容易直接重试。导出副本可能因此产生重复文件；带有覆盖或发布行为的工具，影响还会更大。

对于这样的写操作，我会考虑由系统分配稳定的操作 ID。同一次导出重试时继续使用它，后端据此识别已有操作，并返回状态或结果。

这需要后端真正实现去重和状态记录，不能只让模型在参数里填一个编号。同一个操作 ID 也应对应同一组输入；如果裁切条件已经改变，那就是新的操作。

同时提供查询入口，让超时之后有地方继续查：

```text
导出请求：export_028
当前结果：客户端等待超时，完成状态尚未确认。
下一步：查询 export_028 的状态，再决定是否重新发起。
```

这与“原图尺寸不足”是两种不同的情况。

尺寸不足有明确原因，可以寻找其他候选，或者在得到允许后调整目标条件。完成状态未知，则要先弄清操作有没有发生。

如果都只返回“失败，请重试”，模型就失去了区分它们的依据。

我希望错误结果能够说明哪里没有完成、哪些状态已经改变、还可以从哪里继续查。无需替模型写完全部计划，但至少给它一个可靠的起点。

## 好用，需要放回任务里验证

这些设计听起来合理，还需要验证。

如果实现这个案例，我会保留同一批照片、同一组任务和同一个模型，对比不同版本的接口。每次尽量只改变一个因素：先补清检索范围，再改善结果字段，之后检查预览是否被正确传入。

所有地方一起修改，即使表现变好，也很难知道哪一处起了作用。

验收也要拆开。参数是否有效，候选是否满足明确条件，导出的对象是否对应用户选择，原图是否保留，以及视觉描述有没有相应的输入依据，都可以分别检查。

构图是否合适仍然需要人看，而且应当允许多个合理答案。如果检查器只接受一张预设照片，就可能把有效选择误判成失败。[Anthropic 关于 Agent 评估的文章](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)讨论了按任务组合不同检查方式，以及检查器本身可能带来的偏差。

我还会保留几组没有参与接口调整的任务，看看改进能不能用到新的条件里，并重复运行，观察行为是否稳定。调用次数、耗时和上下文用量也值得记录：一个接口如果需要反复试探才能成功，成本可能只是被藏到了流程中。

更需要准备的是没有合适候选、预览读取失败、候选版本变化，以及导出超时的情况。

“找不到”可以是正确结果。值得检查的是，它有没有说明找过哪里、受到什么限制，以及是否为了完成任务擅自放宽要求。

如果工具已经把范围说清楚，图像也确实提供了，模型仍然忽略关键条件，那就继续检查模型能力、提示和运行过程。工具设计能解决一部分问题，也需要知道自己解释不了哪些问题。

回到那句“画面空一点”，它仍然不会变成一个完全精确的参数。

看到候选之后，我可能才发现想保留的是街灯下面那块空地，而不是让画面里什么都没有。Agent 也可以指出，保留那块空地会让主体偏到边缘，或者这张照片的尺寸不足，换一张更合适。

这样的交流需要具体的东西托住：我们看的是同一张照片、同一个版本，谈论的是同一次裁切。它解释过取舍，也把尚未确定的地方留下了。

这时，我可以指着预览说：“右边再留一点，灯别切掉。”

下一步该调整哪里，双方都知道。
