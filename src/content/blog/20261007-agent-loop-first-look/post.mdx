先设想一件小事：准备发布一篇博客时，发现站内搜索按钮点了没反应。你把问题交给 Coding Agent，过了一会儿，它回复：“已经修好了。”

看到这句话，你大概还是会打开页面，亲手点一下那个按钮。

这个动作很小，却把一个问题摆到了我面前：Agent 说“修好了”，和搜索真的能用了，中间究竟发生了什么？如果它第一次找错了文件，是什么让它换了方向？如果测试通过了、页面却依旧没有结果，它又该相信哪一个？

我想借这个假设中的小任务，把 Agent Loop 放慢来看。它至少涉及三件事：**模型根据已有信息选择下一步，工具把这个选择带进真实环境，反馈把结果送回来。**循环让三者接上，也决定什么时候继续、什么时候停下。

## 一、一次“修好搜索”要走几轮

假设 Agent 接到的要求是：“搜索按钮点了没反应，找出原因并修好。”

它起初并不知道问题在哪。按钮可能没有绑定事件，事件触发了但请求失败，也可能搜索接口返回了数据、页面却没有显示。此时它能做的第一件事，是根据手头的信息选择一个调查入口。

一次可能的过程是：

1. 搜索项目里与搜索按钮有关的代码。
2. 读取页面组件和搜索逻辑，检查事件从哪里开始、走到哪里。
3. 如果代码看不出问题，查看运行错误，或在浏览器里复现。
4. 提出修改，执行改动。
5. 运行相关检查，必要时再次打开页面。
6. 根据结果继续修正，或者说明任务已经完成。

这份清单看起来像预先写好的脚本。实际运行时，后一步往往取决于前一步：搜索没有结果，就换关键词；发现按钮事件正常触发，就把注意力转向请求和渲染；测试失败，就读报错再修改。

[OpenAI Agents SDK 对 Agent Loop 的说明](https://openai.github.io/openai-agents-js/guides/running-agents/)把它描述得很直接：调用模型，检查回复；如果模型请求工具，就执行工具、把结果加入上下文，然后再次调用模型。模型也可能给出最终回答，或者把任务交给另一个 Agent。

所以，Loop 不一定是一套复杂的架构。它最基本的能力，是让“下一步做什么”随着新信息改变。

## 二、模型提出行动，外面的程序执行行动

这里需要分清两个容易连在一起的动作：模型**请求读取文件**，以及文件**真的被读到**。

模型接收任务、对话历史、工具说明和已经返回的结果，然后生成下一步回复。这个回复可以是一段给用户看的文字，也可以包含工具调用，例如“读取这个文件”或“运行这条检查命令”。

工具调用只是请求。外面的程序还要识别它、检查参数与权限、实际执行，再把结果交还给模型。[Anthropic 的工具使用文档](https://docs.anthropic.com/en/docs/agents-and-tools/tool-use/overview)也清楚地区分了模型提出工具请求、客户端执行工具、返回工具结果这几个步骤。

这个区别让我重新理解了“模型会使用工具”这句话。模型可以判断应该查看哪个文件，却不会因为判断正确就自动获得读取权限；它可以要求运行测试，却不能用自己的回答替代测试进程的结果。至于某个目录能不能读、某条命令能不能执行，应该由运行环境决定。

工具设计也会影响模型的判断。如果工具只返回“失败”，模型很难知道该检查什么；如果返回的是明确的报错、退出状态和相关位置，它就有机会缩小问题范围。给 Agent 接上工具时，除了问“它能做什么”，还要问“做完之后，它能看见什么”。

## 三、反馈不是一句“成功”或“失败”

回到搜索按钮。假设 Agent 改完代码，运行类型检查，工具返回“通过”。这是一个真实结果，但它证明的是**类型检查通过**，还不能证明**搜索按钮能正常工作**。

它至少可能漏掉两种情况：按钮在浏览器里仍然没有触发搜索；或者搜索能发出请求，却在“没有结果”时显示一片空白。检查各有覆盖范围。把其中一项通过写成“问题已经解决”，相当于跳过了其余问题。

我会把反馈分成三层来看：

- **动作是否执行**：文件是否读到，命令是否启动，浏览器操作是否完成。
- **局部结果是什么**：测试通过了哪些用例、失败在哪里，页面出现了什么。
- **结果是否满足原目标**：用户说的“搜索能用”，在实际使用中是否成立。

前两层通常可以由工具返回。第三层要回到最初的任务，有时还需要人参与判断。反馈越具体，模型越有可能发现自己只完成了一部分；反馈越含糊，它越容易沿着一个错误的判断继续走下去。

[ReAct 论文](https://arxiv.org/abs/2210.03629)讨论过让模型的推理与行动交替发生，再利用外部观察推进任务。今天的 Agent 可以有不同实现，但“做一步、看结果、再决定下一步”仍是理解 Loop 的一个好入口。

这里的“反馈”指本次任务中的观察结果。它不会因为被送回模型，就变成一次模型训练。它改变的是模型这一轮接下来能依据什么作出判断。

## 四、让结果回来，还得让模型看得懂

循环运行久了，会遇到另一个问题：工具结果会越来越多。

一次代码搜索可能找到几十个文件；测试失败可能打印很长的日志；浏览器里也可能同时出现几个错误。如果把所有内容不加区分地塞回下一轮，重要线索反而可能被淹没。模型需要知道的不只是“刚才运行了测试”，而是**哪项检查失败、失败位置在哪里、它与当前任务有什么关系**。

但压缩结果也有风险。若只留下“检查失败”，模型失去了定位问题的依据；若整理结果的程序误删了关键报错，后续判断就会建立在残缺的信息上。上下文管理因此不只是节省空间，也是在决定 Agent 能依据哪些证据继续工作。

这让我觉得，Loop 里的“反馈”更接近一份交接记录。好的交接既不把整间仓库搬过来，也不只留一句“你自己看着办”。它保留下一步决策需要的事实：做过什么、得到了什么、哪里仍然不确定。

## 五、能继续，也要知道什么时候停

Agent 可以一轮接一轮地查下去，但总要有停止条件。

有些停止很直接：模型给出了最终回答；工具出错且无法恢复；运行达到预设的轮次或时间上限。有些则来自任务本身：下一步需要新的权限，或者几种方案涉及产品取舍，应该把选择交还给人。

还有一种更隐蔽的停止：Agent 觉得自己做完了，于是结束。它可能是对的，也可能只验证了最容易验证的部分。

如果我要把“修好搜索按钮”交出去，会更愿意事先说清楚验收条件，例如：能够复现原问题；修改后可以正常发起搜索；有结果和无结果时页面都能合理显示；相关检查通过。这样 Agent 在结束前有一份可以对照的目标，我收到它的报告时，也知道该看哪些证据。

验收条件不必写到每一步操作都由人指定。Agent 的价值恰恰在于，它可以在目标明确的情况下自行调查、调整方法。人需要说清的是**什么结果算完成**，以及**哪些决定不能由它独自承担**。

## 六、读 Agent 代码时，我会先找这四个位置

把上面这些拼起来，Agent Loop 可以粗略写成四步：

1. 把任务和现有上下文交给模型。
2. 读取模型的回复。如果它请求工具，就在允许的范围内执行。
3. 把工具结果加入上下文，再次调用模型。
4. 如果它给出最终回答，就结束这一轮任务。

真实系统还要处理工具失败、权限、运行上限和中断恢复。但第一次读一个 Agent 项目的代码时，我会先找四个位置：**模型在哪里被调用，工具请求在哪里执行，结果怎样进入下一轮，以及运行由谁结束。**

找到这四处，再看其他设计会清楚很多。记忆决定过去的信息怎样进入当前上下文；权限决定请求能否变成行动；日志和检查决定人事后能否看清发生了什么。它们都与 Loop 有关，但不必一开始就把所有概念一起背下来。

也不是每段会调用模型、执行工具的程序都需要被称作 Agent。一个步骤完全固定的流程，照样可以很有用。这里让我感兴趣的，是模型会根据返回的结果选择后续行动：第一次判断可以被事实修正，接下来的路径可以随任务变化。

## 最后，回到那个搜索按钮

文章开头，我在想：Agent 回复“已经修好了”之后，为什么我还想亲手点一下按钮？

现在这个动作对我有了更具体的含义。我点开的不是一份对模型能力的不信任，而是任务最后一段证据：它修改的是不是我在意的问题，页面是否真的像预期那样工作。Agent 可以替我调查、尝试和检查，也应该如实告诉我哪些地方没检查到。这样我花在验收上的时间，才可能比自己从头处理更少。

我希望以后能把更多工作交给 Agent，不必盯着它每一步怎么做。要做到这一点，关键不是让它每次都说得更有把握，而是让它能接触真实结果、根据结果修正自己，并在结束时把依据交给我。

模型、工具和反馈接成一个循环，任务才有机会从一句要求走到一个可检查的结果。下次看到“已经完成”，我还是会点一下那个按钮。只是我希望，那时摆在我面前的除了这句话，还有足够清楚的过程，让我知道它为什么这么说。
