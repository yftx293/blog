写上一篇关于上下文管理的文章时，我举过一个例子：让 Agent 给文章列表加标签筛选，同时告诉它，“这次先不新增路由”。

当时，这句话只是一个普通的任务边界。先把眼前的功能做好，其他事情以后再说。

但写完之后，我有点放不下其中两个字：**这次。**

如果 Agent 把这段交流整理进长期记忆，下次再做相关功能时，这两个字还会在吗？

```text
用户偏好：不要新增路由。
```

这条记录很简洁，也方便复用。只是它已经和原话有了一点距离。我们原本只决定了一次任务该怎么做，记忆却替我们决定了以后也该怎么做。

这篇笔记想先把这点距离记下来。它看起来很小，却可能影响 Agent 后面很多轮的判断。

## 记住了决定，却丢掉了条件

“这次先不新增路由”包含一个决定，也包含它的适用范围。

如果整理时只留下“不新增路由”，一次局部取舍就可能变成用户偏好。再经过几次引用，它甚至会被写进项目约束。

这里未必有凭空编造的信息。更值得留意的是，概括改变了原话的含义：从“这次这样做”，变成“以后都这样做”。

假设下一次，我明确要求给每个标签建立独立页面。Agent 却回答：“考虑到你不希望新增路由，我会继续使用页面内筛选。”

它记得我说过什么，却没有记住我是在什么情况下说的。

我目前觉得，判断一条记忆是否正确，至少要分开看两件事：它有没有忠实记录过去，以及它是否适用于当前任务。

“上一次没有新增路由”可以一直是准确的历史事实。但这段历史能否约束今天的行动，需要重新判断。**长期保存，并不意味着长期适用。**

## 我暂时想保留什么

如果要保存这个决定，我现在更倾向于留下这样的记录：

```text
决定：本次标签筛选在页面内完成，不新增路由。
范围：这一次标签筛选任务。
来源：用户在本次对话中的明确要求。
原因：未明确说明，不推断为长期架构限制。
后续：其他任务涉及路由时，结合当时的要求重新判断。
```

比起“用户不喜欢新增路由”，它啰嗦了一些。但多出来的内容，恰好是以后判断是否适用时需要的依据。

其中，我尤其想保留“原因未明确说明”。

我们很容易替一个决定补上解释：也许用户想保持 URL 稳定，也许觉得路由太复杂，也许只是今天想少做一点。每一种解释都说得通，却不一定是当时的理由。

解释如果没有标明是推测，下一轮就可能被当作事实继续使用。最初那句很具体的要求，反而越来越难找到了。

所以，保存来源也有意义。简短摘要可以帮助检索；真正需要依据它做决定时，最好还能回到原话。特别是“暂时”“这次”“只针对这个页面”这些词，它们并不是可以随手删掉的修饰。

不过，这份记录还只是一种设想。字段齐全，并不能保证模型会正确使用它们。我更看重的是：出了问题以后，我们能够检查，究竟是写入时丢了条件，还是读取时忽略了条件。

## 有效期，不一定是一段时间

[Anthropic 的 Memory tool 文档](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool#memory-expiration)在记忆过期部分给出了一条建议：定期清理长期没有被访问的记忆文件。

这让我想到另一种情况：一条记忆经常被读取，却早已不适用于眼前的工作。

如果“不要新增路由”每次都被检索出来，它的最近访问时间会不断更新。但这些访问没有提供新的确认，只是在重复使用同一个旧决定。

**被读取很多次，和被用户确认很多次，应该分开看。**

对临时决定来说，任务是否结束、需求是否改变、用户是否给出了新的明确要求，可能比过去了多少天更重要。

这里的“过期”，也未必意味着要删除。

旧决定仍然可以解释代码为什么长成现在这样：当时为什么用了页面内筛选，为什么没有建立独立页面。这些信息对维护有帮助。只是它应该作为历史被查到，而不再自动成为新任务的限制。

我想尝试区分“当前适用”“历史记录”和“需要复核”。但还有个问题没解决：谁来改变这个状态？

明确的新要求可以提供更新依据。至于含糊的情况，我不希望 Agent 仅仅因为旧约束让任务变难，就自行认定它已经失效；也不希望它遇到任何旧记录，都停下来让我重新确认。

需要确认到什么程度才合适，这部分还没有想清楚。

## 先做一个小对照

我还没有做实验，想先从两个连续任务开始。

第一个任务明确要求：“本次标签筛选不新增路由。”第二个任务则明确要求：“为每个标签新增独立页面和路由。”

分别给 Agent 两种记忆：一种只保存“不要新增路由”，另一种保留原话、适用范围和来源。其余条件尽量保持一致，再重复几次，观察差异。

我想看的不只是第二个任务最终有没有完成，还包括：

- 第一次的限制是否被正确遵守；
- 第二次是否仍被旧记录阻碍，或出现多余的确认；
- Agent 解释决定时，能否区分当前要求和历史取舍。

这个对照只能验证范围信息有没有帮助。两个任务之间的变化很明确，实际交流通常没有这么整齐。用户可能只说“现在把标签页面补上吧”，既没有重述旧决定，也没有正式宣布它失效。

如果明确场景都处理不好，就先检查记忆写入和读取的过程。如果能处理好，再看模糊场景：它能否指出哪里不确定，以及这点不确定是否真的值得打断用户。

我也还不准备给每条记忆都加上完整的生命周期。维护这些信息本身有成本。也许先从那些会影响后续行动的决定做起，比整理所有历史更实际。

暂时想验证的是：当我改变了任务范围，Agent 能不能理解这次变化，而无需我先纠正一个被它概括出来的“长期偏好”。这件事如果能做好，再继续讨论它该记住多少。
